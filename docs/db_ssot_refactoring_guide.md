# SSOT DB 마이그레이션 가이드

## 목적

`weekly_change` 도메인을 xlsx+매니페스트 파이프라인에서 krx-auto-crawling
발행 SQLite DB 구독 방식으로 리팩토링하며 얻은 교훈을 정리한다. 이후
`netbuy`, `ceiling`, `new_listing`, `bonus_issue` 등 이미 SSOT DB가 발행된
다른 도메인을 같은 방식으로 옮길 때 이 문서를 체크리스트로 쓴다.

동기화 프로토콜 자체(매니페스트 구조, 원자적 갱신 절차)는
[`db_ssot_consumer_sync.md`](./db_ssot_consumer_sync.md)를 따른다. 이
문서는 "그 규약을 실제 도메인에 적용할 때 무엇을 조사하고, 무엇을
조심해야 하는가"를 다룬다.

## 착수 전 조사 (Discovery)

### 1. Drive 폴더 구조는 도메인마다 다르다 — 가정하지 말고 직접 확인

`weekly_change`는 `db/{weekly,monthly}/{year}.db`였지만, 같은 프로젝트
안에서도:

- `netbuy`(sd 폴더)는 `market_data_{year}.db`가 폴더 **최상위**에 바로 있음
- `ceiling`은 `db/{year}.db`
- `new_listing`은 `db/{year}.db`이지만 아직 특정 연도만 존재
- `bonus_issue`는 연도 구분 없는 **단일 파일** `무상증자.db`

새 도메인을 옮기기 전에 반드시 Drive를 실제로 리스팅해서 경로 패턴을
확인한다. 기존 xlsx 폴더 구조(`{year}/{month}월/...`)와 새 `db/` 구조가
같은 최상위 폴더 아래 공존하는 경우가 많다 — 생산자가 전환 기간 동안
두 포맷을 함께 발행 중이라는 뜻이다.

**단, 한 도메인 안에 여러 "주기 타입"이 있고 스키마가 동일하다면 구현을
통째로 재사용한다.** `weekly_change`의 `weekly/`와 `monthly/`는 폴더만
다를 뿐 `events`/`items` 스키마가 완전히 같아서, 동기화·조회 코드를
전부 공유하고 `is_monthly` 플래그 하나로만 분기했다. 새 도메인에도
일간/주간/월간처럼 여러 주기가 있다면, 별도 구현을 만들기 전에 먼저
스키마가 같은지 확인한다 — 같다면 도메인별 코드가 아니라 주기별
파라미터 하나로 끝난다.

### 2. 스키마는 도메인마다 다르고, 조사 시점에도 바뀔 수 있다

다섯 도메인을 조사한 결과 테이블/컬럼이 전부 달랐다 (`netbuy`+`price_info`,
`cohort_stocks`+`price_history`+`collection_log`, `stocks`(단일 테이블),
`bonus_shares_decisions`, `events`+`items`). 공유 스키마를 가정하지 말고
도메인별로 직접 다운로드해서 `PRAGMA table_info`로 확인한다.

**스키마는 조사 도중에도 바뀔 수 있다.** 이번 작업 중 `items` 테이블에
`in_kospi200`/`in_kosdaq150` 컬럼이 조사 세션 도중 추가됐다(생산자가
그 사이에 재발행). 설계를 확정하기 직전, 구현 시작 직전에 한 번 더
최신 스키마를 재확인하는 습관이 필요하다 — 특히 사용자가 "DB 갱신했다"고
알려주면 무조건 다시 받아서 확인한다.

### 3. 필드 의미는 실제 사용처를 보고 판단한다

새 DB의 필드가 기존 도메인 모델의 필드와 이름/모양이 비슷해 보여도
**의미가 다를 수 있다**. `kospi_200_items`가 매주 고정 200개(지수
구성종목 전체)였다는 사실은 로컬에 저장된 실제 JSON 리포트 몇 개를
열어봐야 알 수 있었다 — 필드 설명이나 스키마만 봐서는 몰랐다.

체크리스트:
1. 기존 로컬 캐시(JSON 등)에 남아있는 실제 값의 개수/패턴을 확인한다.
2. 그 필드를 프론트엔드/라우트가 실제로 어떻게 쓰는지(`grep`)를 확인한다.
3. "새 DB에 없는 것 같은 필드"를 발견해도 바로 기능 축소로 단정하지
   말고, 실제로 필요한 게 그 필드의 표면적 의미인지 다시 사용자에게
   확인한다. (이번엔 "지수 구성종목 전체"가 아니라 "급등주 ∩ 지수 소속"이
   실제 요구사항이었고, 마침 새 DB의 플래그 컬럼이 정확히 그걸 제공했다.)

## 설계 시 주의점

### 매니페스트는 항상 구독자 로컬 전용

생산자는 구독자의 캐시 상태를 모르고 알 필요도 없다. 매니페스트 스키마와
동기화 결정 매트릭스(재사용/재다운로드/매니페스트만 재생성/실패 시 stale
유지)는 `db_ssot_consumer_sync.md`를 그대로 따르면 된다 — 도메인마다
새로 설계할 필요 없음.

### 원격 메타데이터 확인 TTL — 2026-08-31 수정 완료, 다음 마이그레이션은 처음부터 넣을 것

`db_ssot_consumer_sync.md`는 원격 메타데이터 확인을 "서버 시작 시 1회 /
명시적 동기화 시 / 짧은 TTL(10~30분) 경과 후 첫 요청"으로 제한하라고
명시했는데, `WeeklyChangeDbSync.ensure_year_db`는 처음엔 이 권고를
구현하지 않고 호출될 때마다 무조건 Drive에 `list_files_in_folder` +
`get_file_metadata`를 날렸다. `list_available_dates()`가 연도 3개 ×
주기 2종을 순회해서, 날짜 드롭다운을 열 때마다 Drive API가 12회
호출되는 게 실사용 중 발견돼 20분 TTL로 고쳤다(매니페스트에
`last_checked_at` 추가, `_within_ttl()`로 판단).

**이 수정 자체가 새 버그를 만들 뻔했다 — 교훈으로 남긴다.** TTL을
`ensure_year_db` 레벨에만 넣었더니, UI의 수동 새로고침
(`force_sync=True` → `/api/statistics/weekly-change?force_sync=true`)을
눌러도 TTL 이내면 그냥 낡은 로컬 DB를 반환해버리는 회귀가 바로
생겼다. `get_weekly_change(force_sync)` → `sync_data()` →
`_sync_for_year`/`_sync_latest` → `ensure_year_db()`까지 호출 체인이
길었는데, 중간 계층들이 `force`를 그냥 삼키고 있었던 것이다.
**TTL을 도입하면 "명시적 동기화 요청은 TTL을 무시해야 한다"는 요구사항이
반드시 함께 따라온다(§ "동기화 알고리즘" 1항이 이미 이렇게 명시하고
있었다) — TTL 캐시를 만드는 순간, 그 캐시를 우회하는 경로가 호출
체인 끝까지 실제로 뚫려 있는지 매 계층에서 확인할 것.** 다음
도메인(`ceiling` 등)을 옮길 때는 TTL과 force 우회를 같은 커밋에서
설계하고, "force_sync=True면 TTL 캐시가 실제로 원격을 재확인하는지"를
회귀 테스트로 반드시 남긴다.

### "날짜 기반 캐시 키"는 진행 중인 기간에서 반드시 버그를 만든다

이번에 실사용 중 발견한 버그 두 개가 전부 같은 원인에서 나왔다:

- 아직 확정(final)되지 않은 기간(이번 주, 이번 달)은 재수집될 때마다
  `last_trading_day`(기준일)가 하루씩 앞으로 이동한다.
- 로컬 캐시 파일명이나 dedup 키를 **정확한 날짜**로 잡으면, 같은 주/월인데
  날짜만 다른 스냅샷이 별개 항목으로 계속 쌓이거나(중복 표시), 다른
  주기 타입(weekly vs monthly)의 우연한 날짜 일치로 서로를 가려버린다.

**교훈**: 캐시/dedup 키는 "정확한 날짜"가 아니라 "기간 식별자"
(연도+주차 또는 연도+월, +주기 타입)로 잡아야 한다. 이벤트의
`id`(`YYYY-Www` / `YYYY-Mmm` 형식)가 이미 이 식별자 역할을 하므로,
가능하면 그 자체를 키로 쓰는 게 가장 안전하다. 새 도메인에도 "진행
중 상태가 있는 시계열" 데이터(주간/월간/일간 집계 등)라면 이 문제가
똑같이 재현될 수 있으니 설계 단계에서 미리 점검한다.

### 공개 계약은 유지한다

서비스의 메서드 시그니처와 반환 타입(`get_X`, `sync_data`,
`list_available_dates` 등)은 그대로 두고 내부 구현만 교체한다. 라우트와
프론트엔드는 전혀 손대지 않아도 되도록 설계하면 회귀 위험이 줄어든다.
바뀌는 게 있다면(이번엔 없었지만) 먼저 사용처를 `grep`으로 전수 확인한다.

## 구현 순서 (TDD)

이번에 효과가 검증된 순서:

1. **Drive 어댑터에 필요한 필드가 없으면 먼저 추가** (`md5Checksum` 등).
   기존 메서드에 필드만 얹는 최소 변경 + 회귀 어서션.
2. **DB 동기화 컴포넌트**(원격 대조/다운로드/검증/매니페스트)를 독립
   모듈로 먼저 TDD. Drive 어댑터는 mock, 로컬 파일 I/O는 `tmp_path`로
   실제 SQLite 파일을 만들어 검증한다 — 동기화 결정 매트릭스(재사용/
   재다운로드/매니페스트 없음/원격 실패/다운로드 손상 등)를 전부
   케이스로 만든다.
3. **SQL 조회 계층**을 독립 모듈로 TDD. **실제 프로덕션과 동일한 스키마로
   만든 fixture DB**에 대해 쿼리 함수를 검증한다 — mock이 아니라 진짜
   SQLite를 써야 SQL 문법 오류나 컬럼명 오타를 이 단계에서 잡는다.
4. **서비스 계층**을 새 컴포넌트들을 조립하도록 재작성. 기존 서비스
   테스트 중 내부 구현(삭제된 private 메서드)에 결합된 것은 과감히
   삭제하고, 공개 계약 기준으로 새로 작성한다.
5. **정적 분석(ruff/ty/radon)을 컴포넌트 단위로 그때그때 통과시킨다.**
   끝에 몰아서 하면 복잡도 초과 지점을 어느 커밋에서 고쳐야 할지
   헷갈린다. `radon cc -n C`가 C 이상을 보고하면 그 자리에서 헬퍼
   메서드로 쪼갠다.
6. **전체 회귀 스위트를 최소 1회는 반드시 통과 상태로 만든다.** 실패가
   나오면 `git stash`로 변경 전 상태에서도 같은 테스트를 돌려 기존
   실패인지 내가 만든 회귀인지 반드시 구분한다 — 구분 없이 "기존
   실패겠지"라고 넘기면 진짜 회귀를 놓친다.
7. **실 Drive 데이터로 최종 검증한다.** 이번 두 버그는 전부 단위
   테스트가 아니라 실제 서비스를 실 Drive에 대해 돌려봐서 발견했다.
   합성 테스트 데이터는 우연한 날짜 충돌 같은 실데이터의 지저분한
   패턴을 재현하지 못한다. 마이그레이션 마지막 단계로 반드시
   "실제 서비스 메서드를 실제 데이터로 호출해서 눈으로 결과 확인"을
   넣는다.
8. 버그를 발견하면 **회귀 테스트로 먼저 재현(Red) 후 수정(Green)** —
   실데이터에서 본 정확한 시나리오를 테스트 케이스로 옮긴다.

## 브랜치/커밋 워크플로우

CLAUDE.md의 리팩토링 워크플로우(브랜치 생성 → TDD 반복 → 회귀 확인 →
DoD 체크 → `--no-ff` 병합)를 그대로 따르면 된다. 실제로 효과가 좋았던
부분: 컴포넌트 하나가 완성될 때마다(동기화 관리자, 조회 계층, 서비스
교체, 버그 수정 각각) 별도 커밋으로 쪼개서, 병합 커밋에서 전체 변경을
설계 결정과 함께 요약했다 — 나중에 이 문서를 쓸 때도 커밋 로그만
보고 타임라인을 복원할 수 있었다.

## 다음 마이그레이션 후보 우선순위 메모

조사 시점(2026-08-27) 기준 SSOT DB가 이미 발행된 도메인:

- `netbuy` — 원 설계 문서의 기준 예시. 스키마가 가장 단순(`netbuy`,
  `price_info` 2테이블)해서 다음 후보로 적합.
- `ceiling` — DB 용량이 큼(2026년치 11.8MB, `price_history` 14만 행).
  성능/캐시 전략을 더 신경 써야 할 수 있음.
- `new_listing` — 2026년치만 존재, 컬럼이 27개로 많음(신규상장 스펙
  전체). 과거 연도 DB가 아직 없어 이번처럼 "여러 연도 순회" 로직이
  단순해질 수 있음.
- `bonus_issue` — 연도 구분 없는 단일 파일이라 `WeeklyChangeDbSync`의
  "연도별 파일" 가정이 그대로는 안 맞음. 매니페스트 키 설계를 다시
  해야 함.
