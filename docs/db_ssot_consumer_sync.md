# DB SSOT 구독자 동기화 규약

## 목적

여러 수집 프로젝트가 Google Drive 등에 작은 SQLite DB 파일을 발행하고, 이 프로젝트처럼
그 결과를 **읽기 전용으로 구독하는 프로그램**이 안전하게 최신 데이터를 사용하기 위한 공통
규약이다.

이 문서는 `krx-auto-crawling`이 발행하는 `market_data_{year}.db`를 첫 적용 대상으로 한다.
같은 방식은 상한가, 신규 상장, 주간 등락률 등 다른 수집 결과에도 적용할 수 있다.

## 책임 경계

```text
수집 프로젝트                  구독 프로젝트 (예: mindmap)
──────────────────────────     ──────────────────────────────────
DB를 완성해 원격 저장소에 발행  원격 DB 변경 여부를 확인
DB 스키마와 데이터 품질 보장    필요한 DB를 로컬 캐시로 내려받음
원격 DB의 유일한 원본(SSOT)     로컬 DB를 읽기 전용으로 조회
                                구독 상태 매니페스트를 자체 관리
```

- **원격 DB**가 최종 원본(SSOT)이다.
- **로컬 DB**는 실제로 조회하는 캐시다. 파일이 존재한다고 정상으로 간주하지 않는다.
- **매니페스트**는 구독자의 캐시 상태 기록이다. 원격 DB의 원장도, 데이터 최신일의 원장도 아니다.
- 구독자는 DB를 수정하거나 원격 저장소에 재업로드하지 않는다.

## 매니페스트의 역할과 위치

매니페스트는 구독 프로그램의 데이터 디렉터리에 DB와 함께 둔다.

```text
data/statistics/netbuy/
├── market_data_2025.db
├── market_data_2026.db
└── manifest.json
```

각 원격 파일에 대해 아래 정보를 저장한다.

```json
{
  "schema_version": 1,
  "files": {
    "market_data_2026.db": {
      "drive_file_id": "remote-file-id",
      "remote_modified_time": "2026-08-25T06:45:16Z",
      "remote_md5_checksum": "...",
      "remote_size_bytes": 3788800,
      "local_sha256": "...",
      "local_size_bytes": 3788800,
      "data_max_date": "2026-08-25",
      "downloaded_at": "2026-08-26T01:00:00Z",
      "integrity_checked_at": "2026-08-26T01:00:00Z"
    }
  }
}
```

`data_max_date`는 UI의 “데이터 기준일” 표시와 운영 점검을 위한 값이다. 원격 파일의 변경 여부를
판단하는 데에는 사용하지 않는다. 그 판단은 Drive의 파일 ID, 수정 시각, 체크섬, 크기를 사용한다.

## 동기화 알고리즘

### 1. 원격 메타데이터 확인

Drive에서 DB 파일의 본문을 다운로드하지 않고 `id`, `name`, `modifiedTime`, `md5Checksum`, `size`만
조회한다. 이 호출은 가볍지만, 요청마다 실행할 필요는 없다.

- 서버 시작 시 1회 확인
- 사용자가 명시적으로 동기화할 때 확인
- 선택적으로 짧은 TTL(예: 10~30분)이 지난 첫 요청에서 확인

### 2. 로컬 캐시 사전 검증

매니페스트가 최신이라고 해도 로컬 파일을 신뢰하지 않는다. 사용 전 다음을 확인한다.

1. 파일 존재 여부
2. 파일 크기와 매니페스트의 `local_size_bytes` 일치 여부
3. SHA-256과 `local_sha256` 일치 여부
4. `PRAGMA integrity_check` 결과가 `ok`인지
5. 기대 SQLite 테이블과 필수 컬럼이 존재하는지
6. `MAX(date_str)`가 `data_max_date`와 일치하는지

`market_data` DB의 최소 기대 스키마는 `netbuy`와 `price_info` 테이블이다.

### 3. 다운로드 또는 재사용 결정

| 매니페스트 | 로컬 DB | 원격 메타데이터 | 처리 |
|---|---|---|---|
| 있음 | 정상 | 일치 | 로컬 DB 재사용 |
| 있음 | 없음 또는 손상 | 무관 | 캐시 미스로 보고 재다운로드 |
| 있음 | 정상 | 불일치 | 새 DB 다운로드 |
| 없음 | 정상 | 일치 | 검증 후 매니페스트 재생성 |
| 없음 | 없음 | 존재 | 최초 다운로드 |
| 무관 | 무관 | 원격 확인 실패 | 정상 검증된 로컬 DB만 `stale` 상태로 사용 |

로컬 DB가 없거나 손상됐고 원격 확인/다운로드도 실패하면, 빈 값으로 정상 응답하지 않는다. 동기화
실패를 명확히 반환해야 데이터가 없는 상황을 정상 데이터처럼 오인하지 않는다.

## 원자적 갱신 절차

매니페스트가 DB보다 먼저 최신 상태를 기록하면 안 된다. 반드시 아래 순서를 지킨다.

```text
1. 원격 DB를 같은 디렉터리의 임시 파일로 다운로드
2. 임시 DB의 해시, 크기, SQLite 무결성 및 스키마 검증
3. 데이터 기준일(MAX(date_str)) 계산
4. 임시 파일을 대상 DB로 원자적 교체
5. 새 DB 정보를 담은 매니페스트를 임시 파일에 저장
6. 매니페스트도 원자적으로 교체
```

프로세스가 중간에 종료되어도 다음 실행에서 사전 검증이 불일치를 감지해 복구한다.

- DB만 새 파일이고 매니페스트가 이전 버전이면: 원격 메타데이터 비교 후 무해하게 재동기화한다.
- 매니페스트만 새 파일인데 DB가 없거나 손상됐으면: 로컬 검증 실패로 재다운로드한다.

손상 파일은 조사 필요 시 별도 격리 경로로 옮길 수 있으나, 자동 복구 경로는 원격 원본을 다시
받는 것이 기준이다.

## 조회 규칙

- 웹/API 요청은 원격 Drive가 아니라 **로컬 SQLite만 읽는다**.
- 조회 전 보유한 DB 연결은 읽기 전용으로 열고, 쓰기·스키마 변경을 허용하지 않는다.
- 연도별 파일 구조라면 요청 날짜 또는 조회 범위에서 필요한 연도 DB를 선택한다.
- 연도 경계 조회(예: 1월 초의 직전 거래일)는 이전 연도 DB까지 명시적으로 탐색한다.
- 응답에 데이터 기준일과 상태(`fresh`, `stale`)를 제공하면 UI와 운영자가 데이터 신선도를 알 수 있다.

## 동시성

같은 프로세스에서 중복 동기화 요청이 들어오지 않도록 DB 파일 단위 잠금을 둔다. 여러 프로세스가
동일한 로컬 데이터 디렉터리를 공유한다면 운영체제 파일 잠금도 추가한다.

동기화 중에는 기존 DB를 유지하고, 검증이 끝난 뒤 원자적으로 교체한다. 따라서 진행 중인 읽기 요청은
이전의 정상 DB를 읽고, 이후 요청은 새 DB를 읽는다.

## 관측성과 실패 처리

동기화마다 다음을 로그/상태로 남긴다.

- 원격 파일명, ID, 수정 시각, 크기, 체크섬
- 캐시 판정 결과(재사용, 캐시 미스, 원격 변경, 손상 복구)
- 다운로드 및 검증 성공/실패 사유
- 로컬 DB의 데이터 기준일과 캐시 상태

원격 메타데이터 확인이 일시적으로 실패했을 때는 마지막으로 검증된 로컬 DB를 제공할 수 있다.
단, 이때는 반드시 `stale` 상태를 기록·노출하고, 다음 동기화 기회에 다시 원격과 비교한다.

## 적용 체크리스트

- [ ] 수집 프로젝트가 DB 스키마와 파일명 규칙을 문서화했다.
- [ ] 전환 전 필요한 과거 데이터가 원격 DB에 모두 백필됐다.
- [ ] 구독 프로젝트에 DB별 캐시 디렉터리와 매니페스트를 만들었다.
- [ ] 원격 메타데이터 비교와 로컬 무결성 검증을 모두 구현했다.
- [ ] 다운로드와 매니페스트 저장을 원자적으로 처리한다.
- [ ] 기존 엑셀 파일 존재 여부 기반의 완료/스킵 판단을 제거했다.
- [ ] 조회 코드는 로컬 DB만 읽고, DB를 수정하거나 재업로드하지 않는다.
- [ ] 연도·기간 경계와 네트워크 실패 시나리오를 테스트했다.
- [ ] 데이터 기준일 및 `fresh`/`stale` 상태를 API 또는 운영 로그에 노출한다.
